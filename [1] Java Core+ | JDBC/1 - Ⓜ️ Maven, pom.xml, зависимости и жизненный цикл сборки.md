# Ⓜ️ Maven, `pom.xml`, зависимости и жизненный цикл сборки
## Ⓜ️ Что такое Maven
### `Maven - это инструмент для автоматизации сборки Java-проектов и управления зависимостями.`
### Он делает процессы сборки приложения простыми.
### Позволяет быстро добавлять/удалять сторонние библиотеки и управлять их версиями.
### Многочисленные плагины для Maven помогают автоматизировать работу с проектом.
## ❓ Зачем это нужно и какую проблему решает
### До инструментов сборки программисты вручную:
### - Скачивали `.jar`-файлы библиотек с файлов.
### - Клали их в папку `lib`
### - Прописывали classpath руками в команде `javac`/`java`
### - У каждого разработчика в команде мог быть свой набор версий библиотек - и код у одного работал, а у другого нет.
## ❗ Maven решает три ключевые проблемы
### 1. Управление зависимостями - библиотеки скачиваются автоматически из central-репозитория по имени и версии, а не вручную.
### 2. Стандартизация структуры проекта - любой Java-разработчик, открыв Maven-проект, сразу знает, где искать исходный код, ресурсы, тесты, потому что структура одинакова у всех Maven-проектов.
### 3. Автоматизация сборки - компиляция, тестирование, упаковка в JAR выполняются одной командой по стандартному сценарию (жизненному циклу), а не набором ручных шагов.
## ⚙️ Как это работает внутри
### В корне проекта лежит файл `pom.xml` (Project Object Model). Это XML-файл-описание проекта: кто он, какие у него зависимости, какая версия Java используется, какие плагины подключены.
### Минимальный `pom.xml` выглядит так:
    <project xmlns="http://maven.apache.org/POM/4.0.0">
    <modelVersion>4.0.0</modelVersion>

    <groupId>com.example</groupId>
    <artifactId>my-app</artifactId>
    <version>1.0-SNAPSHOT</version>

    <properties>
        <maven.compiler.source>17</maven.compiler.source>
        <maven.compiler.target>17</maven.compiler.target>
    </properties>

    <dependencies>
        <dependency>
            <groupId>org.postgresql</groupId>
            <artifactId>postgresql</artifactId>
            <version>42.7.3</version>
        </dependency>
    </dependencies>
    </project>
### Разберем ключевые части:
### `groupId` - идентификатор организации/автора (обычно обратное имя домена: com.example).
### `artifactId` - имя конкретного проекта/модуля.
### `version` - версия проекта. `SNAPSHOT` означает: "версия в разработке".
### `dependencies` - список зависимостей. Каждая зависимость это координаты (`groupId:artifactId:version`) библиотеки, которую нужно скачать.
### Когда мы добавляем зависимость и запускаем сборку, Maven:
### 1. Смотрит локальный репозиторий (папка `/.m2/repository` на компьютере) - есть ли уже эта библиотека.
### 2. Если нет  - идет в удаленный репозиторий (по умолчанию Maven Central) и скачивает `.jar` нужной версии, а заодно и все зависимости этой библиотеки (транзитивные зависимости).
### 3. Кладет всё в `/.m2/repository`, чтобы в следующий раз не скачивать заново.
### 4. Подключает эти `.jar` в classpath проекта - теперь мы можем писать `import org.postgresql.Driver;` и это скомпилируется.
## 🔄 Жизненный цикл сборки
### Maven строит проект по фиксированной последовательности шагов - фаз. Это и есть жизненный цикл сборки. Ключевые фазы (в порядке выполнения):
### 1. `validate` - проверка, что структура проекта корректна.
### 2. `compile` - компиляция исходного кода из `src/main/java` в `.class`-файлы.
### 3. `test` - запуск тестов из `src/test/java`
### 4. `package` - упаковка скомпилированного кода в `.jar` (или `.war` для веб-приложений).
### 5. `verify` - дополнительные проверки качества.
### 6. `install` - установка выбранного `.jar` в локальный репозиторий (`~/.m2`), чтобы другие проекты на этой машине могли его использовать как зависимость.
### 7. `deploy` - публикация в удаленный репозиторий (для команд/продакшена).
## 🔁 Часто используемые команды
### `mvn compile` - скомпилировать код.
### `mvn test` - скомпилировать + прогнать тесты.
### `mvn package` - скомпилировать + тесты + собрать .jar
### `mvn clean` - удалить папку target (результаты предыдущей сборки).
### `mvn clean package` - частая связка: сперва стереть старые артефакты сборки, потом собрать заново с нуля.
## ❌ Частые ошибки новичков
### 1. Указание неверной версии зависимости или использования версии, которая конфликтует с другой зависимостью.
### 2. Забыть, что `target/` - генерируемая папка, и если вручную редактировать там - все изменения потеряются при следующей сборке.
### 3. Путать `mvn install` и `mvn package` - `package` просто создает jar в `target/`, `install` дополнительно копирует его в `~/.m2`, откуда его могут использовать другие локальные проекты.
### 4. Не понимать транзитивные зависимости - думать, что если добавить одну библиотеку то получим только её, хотя на деле подтягивается целое дерево зависимостей.
### 5. Неправильные отступы/незакрытые теги в XML.

## ✔️ Контракт `equals()` и `hashCode()`
### Что означает «контракт»
В Java у `equals()` есть набор правил, которым реализация должна соответствовать.

Это не просто написать метод, который вернет `true` или `false`. Другой код имеет право ожидать, что этот метод ведет себя предсказуемо.

Например: `s1.equals(s2)` не должен сегодня вернуть `true`, а через секунду `false`, если значимые данные s1 и s2 не изменились.
## 👌 Рефлексивность
Объект равен самому себе: `a.equals(a)` должно быть `true`
## ✌️ Симметричность
Если: `a.equals(b)` возвращает `true`,

Тогда: `b.equals(b)` тоже должен вернуть `true`.

## 🤟 Транзитивность
Если: `a.equals(b)` возвращает `true`, и `b.equals(c)` тоже возвращает `true`,

С точки зрения `equals()`, тогда `a.equals(c)` должно вернуть `true`.

## 🤝 Согласованность
Если значимые для `equals()` данные не менялись, повторный вызов: `a.equals(b)` должен давать согласованный результат.

## 🕳️ `null`
Объект не должен считаться равным `null`

Для обычного объекта: `a.equals(null)` должно быть: `false`

## ⭐ Главное правило
### Контракт:
Если `a.equals(b) == true`, то `a.hashCode() == b.hashCode()` обязательно.
### Обратное правило не работает:
Если `a.hashCode() == b.hashCode()` это не гарантирует `a.equals(b) == true`.

Потому что возможны коллизии.

## 🔎 Пример правильной реализации
Допустим, `Student` равен по `id`.

    @Override
    public boolean equals(Object obj) {
    if (this == obj) {
    return true;
    }
    
        if (!(obj instanceof Student other)) {
            return false;
        }
    
        return id == other.id;
    }

Теперь `hashCode()` должен использовать тот же значимый признак:

    @Override
    public int hashCode() {
        return Integer.hashCode(id);
    }

Получаем:

`hashCode() → id`

`equals() → id`

Они согласованы.
